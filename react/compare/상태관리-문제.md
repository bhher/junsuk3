import { createContext, useContext } from "react";

function Header() {

function App() {

```jsx
import { createSlice } from "@reduxjs/toolkit";

const counterSlice = createSlice({

    },

```

4. Redux Store가 자동으로 생성된다.

# 해설

## 1. 객관식

### 1. 정답: 2. Props

부모는 자식 태그 속성에 값을 넣고, 자식은 매개변수로 받습니다.

```jsx
<Header user={user} />

function Header({ user }) {
  return <p>{user.name}</p>;
}
```

`useState`는 상태를 만드는 훅이고, `useEffect`는 렌더 이후 부수 효과를 실행하는 훅입니다. Redux는 앱 전체 창고이지, 부모에서 자식으로 넘기는 기본 전달 방법이 아닙니다. `props` 폴더의 `App`이 `Header`에 `user`를 넘기는 방식이 이 문제입니다.

### 2. 정답: 2. useContext

Props만 쓰면 중간 컴포넌트가 값을 사용하지 않아도 받아서 다시 넘겨야 합니다. `useContext`는 Provider가 공급한 값을 필요한 컴포넌트가 직접 꺼냅니다.

`map()`은 배열을 화면 목록으로 바꿀 때 쓰고, `useRef`는 렌더와 무관하게 값을 보관하거나 DOM을 가리킬 때 씁니다. `usecontext` 폴더에서 `MainContent`는 props 없이 `Header`, `Counter`, `UserInfo`만 `useAppContext()`로 값을 읽습니다.

### 3. 정답: 3. 앱 전체에서 공유하는 상태를 체계적으로 관리

Redux는 공유 상태를 store에 두고, 변경 규칙을 slice에 모읍니다. 컴포넌트는 `useSelector`로 읽고 `dispatch`로 변경을 요청합니다. HTML 생성, CSS 변경, 컴포넌트 이름 변경과는 역할이 다릅니다.

### 4. 정답: 1. Props로 전달되는 값

`name`은 `User` 컴포넌트에 넘기는 속성 이름이고, `"홍길동"`이 그 값입니다. 자식에서는 `{ name }`으로 받습니다.

```jsx
function User({ name }) {
  return <p>{name}</p>; // 홍길동
}
```

Redux 액션은 `dispatch(updateName("홍길동"))`처럼 따로 보내고, Provider는 `<AppContext.Provider value={...}>` 형태입니다. 이벤트 함수는 `onClick`처럼 동작에 연결합니다.

### 5. 정답: 1. createContext와 Provider

순서는 세 단계입니다.

1. `createContext()`로 통로를 만듭니다.
2. `<Context.Provider value={...}>`로 값을 공급합니다.
3. 하위 컴포넌트에서 `useContext(Context)`로 꺼냅니다.

`configureStore`는 Redux store를 만들 때 씁니다. `useMemo`와 `useCallback`은 값·함수를 메모이제이션합니다. `BrowserRouter`는 라우팅입니다. `usecontext` 폴더의 `AppContext`와 `AppProvider`가 이 구성입니다.

### 6. 정답: 1. createSlice

`createSlice`는 상태 이름, 초기값, 리듀서를 한곳에서 정의하고 액션 생성 함수를 함께 만듭니다. `redux` 폴더의 `counterSlice`, `userSlice`가 이 도구를 사용합니다.

`createContext`는 Context 통로, `useRef`는 참조 보관, `createElement`는 React 요소 생성입니다.

### 7. 정답: 3. Redux는 여러 컴포넌트가 공유하는 상태를 관리할 수 있다

나머지 설명은 범위가 다릅니다.

1. Props는 그 자식에게 직접 넘기는 값입니다. 전역 상태가 아닙니다.
2. useContext는 중간 컴포넌트를 거치지 않고, Provider 아래 여러 컴포넌트가 같은 값을 읽습니다. 부모 props를 한 단계씩 넘기는 방식이 아닙니다.
3. Redux store에 둔 상태는 연결된 여러 컴포넌트가 읽고 바꿀 수 있습니다.
4. 세 방법은 데이터를 화면에 연결한다는 점은 같지만, 전달 범위와 도구가 다릅니다.

## 2. 코드 분석

### 8. 정답: 2. 안녕하세요, 민수님!

`App`이 `<Greeting name="민수" />`로 문자열 `"민수"`를 넘깁니다. `Greeting`의 `{ name }`은 그 문자열을 받으므로 `{name}` 자리에 `민수`가 들어갑니다.

`name`이라는 글자 그대로가 출력되려면 `{name}`이 아니라 일반 텍스트 `name`이어야 합니다. 컴포넌트는 `h2`를 반환하므로 화면에 문장이 출력됩니다.

이 흐름은 `props` 폴더에서 `<Header user={user} />`가 `user`를 넘기고 `Header`가 `{user.name}`을 그리는 것과 같습니다.

### 9. 정답: 2. 다크 모드

`ThemeContext.Provider`의 `value`가 `"다크"`입니다. `Header`는 Provider 안에서 `useContext(ThemeContext)`를 호출하므로 `theme`은 `"다크"`가 되고, 화면은 `다크 모드`입니다.

`undefined 모드`는 Provider 없이 `useContext`를 호출하거나, `createContext()`에 기본값을 주지 않은 채 Provider 밖에서 읽을 때 나타납니다. 이 코드의 `Header`는 Provider 안에 있으므로 해당되지 않습니다. `"라이트"`라는 값은 코드에 없습니다.

`usecontext` 폴더에서 `AppProvider`가 `value`를 넣고 `Header`가 `useAppContext()`로 `user`를 읽는 구조와 같습니다.

### 10. 정답: 2. value가 1 증가한다.

`increment` 리듀서는 `state.value += 1`만 수행합니다. 초기값이 `0`이면 한 번 실행 후 `1`이 됩니다.

`0`으로 되돌리는 일은 이 코드에 없고, `redux` 폴더에서는 별도 `reset` 리듀서가 `state.value = 0`을 담당합니다. `dispatch`는 컴포넌트를 삭제하지 않습니다. Store는 `configureStore`로 따로 만들며, `dispatch(increment())`가 store를 생성하지는 않습니다.

`counterSlice.js`의 흐름과 같습니다.

```
버튼 클릭 → dispatch(increment()) → reducer 실행 → state.value가 1 증가 → 화면 갱신
```

## 3. 핵심 비교 정리

| 구분 | Props | useContext | Redux Toolkit |
| --- | --- | --- | --- |
| 핵심 목적 | 부모 → 자식 데이터 전달 | 여러 하위 컴포넌트의 값 공유 | 전역 상태의 체계적인 관리 |
| 주요 요소 | 컴포넌트 속성 | createContext, Provider, useContext | createSlice, configureStore, useSelector, useDispatch |
| 적합한 상황 | 버튼 문구, 상품 정보 전달 | 테마, 로그인 사용자 정보 등 | 장바구니, 복잡한 앱 상태 등 |
| 별도 라이브러리 | 불필요 | 불필요 | Redux Toolkit 설치 필요 |

이 프로젝트의 폴더와 대응하면 `props`는 부모에서 자식으로 넘기고, `usecontext`는 Provider 아래에서 필요한 컴포넌트가 꺼내고, `redux`는 slice와 store로 변경 규칙을 모읍니다.
