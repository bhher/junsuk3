# 상태 공유 비교: props / useContext / Redux

같은 화면을 세 폴더에서 각각 다른 방식으로 구현한 예제입니다.

| 폴더 | 방식 | 상태 위치 | 자식이 상태를 받는 방법 |
| --- | --- | --- | --- |
| `props` | Props Drilling | `App`의 `useState` | 부모 → 자식으로 props를 한 단계씩 전달 |
| `usecontext` | Context | `AppProvider`의 `useState` | `useAppContext()`로 필요한 컴포넌트만 꺼냄 |
| `redux` | Redux Toolkit | `store`의 slice | `useSelector`로 읽고 `dispatch`로 변경 |

## 공통 화면

세 앱이 보여주는 화면은 같습니다.

- 헤더: 현재 사용자 이름과 나이
- 카운터: 숫자 표시, `+` / `−` / `Reset`
- 사용자 정보: 이름·나이 표시, 입력 폼으로 변경

초기값도 같습니다.

- `count`: `0`
- `user`: `{ name: "홍길동", age: 25 }`

컴포넌트 트리는 같습니다.

```
App
 ├─ Header                 이름, 나이 표시
 └─ MainContent
     ├─ CounterSection
     │   └─ Counter        숫자 표시, +, -, Reset
     └─ UserSection
         └─ UserInfo       이름·나이 표시, 폼으로 변경
```

상태가 실제로 필요한 곳은 `Header`, `Counter`, `UserInfo`입니다.
`MainContent`, `CounterSection`, `UserSection`은 제목과 배치만 담당합니다.

이름·나이 폼의 로컬 처리도 세 폴더가 같습니다. 입력값은 `UserInfo` 안의 `useState`에 두고, 제출이 성공할 때만 공유 상태를 바꿉니다.

- 이름: 앞뒤 공백을 뺀 값이 있을 때만 반영하고, 입력칸을 비웁니다.
- 나이: 숫자일 때만 `parseInt`로 바꾼 뒤 반영하고, 입력칸을 비웁니다.

---

## 1. `props`

### 문제

`Header`는 사용자 정보가 필요하고, `Counter`는 숫자와 변경 함수가 필요하고, `UserInfo`는 사용자 정보와 변경 함수가 필요합니다. 그 사이에 있는 컴포넌트는 그 값을 화면에 쓰지 않습니다.

상태는 가장 위인 `App`에만 있습니다. 아래 컴포넌트가 그 상태를 쓰려면, 중간 컴포넌트가 값을 받아서 다시 넘겨야 합니다.

### 답

`App.jsx`에서 상태와 변경 함수를 만듭니다.

```jsx
const [count, setCount] = useState(0);
const [user, setUser] = useState({ name: "홍길동", age: 25 });

const updateUserName = (name) => setUser({ ...user, name });
const updateUserAge = (age) => setUser({ ...user, age });
const incrementCount = () => setCount(count + 1);
const decrementCount = () => setCount(count - 1);
const resetCount = () => setCount(0);
```

`{ ...user, name }`은 기존 `user`를 펼친 뒤 `name`만 바꿉니다. `age`는 그대로 남습니다.

전달 경로는 아래와 같습니다.

```
App
 ├─ user ──────────────────────────────► Header
 ├─ user, updateUserName, updateUserAge
 │     count, increment, decrement, reset ─► MainContent
 │                                              ├─ count, 함수 3개 ─► CounterSection ─► Counter
 │                                              └─ user, 함수 2개 ─► UserSection ─► UserInfo
```

파일을 나누면 역할은 이렇습니다.

| 파일 | 역할 |
| --- | --- |
| `src/App.jsx` | `count`, `user`와 변경 함수를 만들고 아래로 전달 |
| `src/components/Header.jsx` | `user`를 받아 이름·나이 표시 |
| `src/components/MainContent.jsx` | 받은 값을 카운터 쪽과 사용자 쪽으로 나눠 전달 |
| `src/components/CounterSection.jsx` | 제목만 그리고 `Counter`에 다시 전달 |
| `src/components/Counter.jsx` | 숫자 표시, 버튼에 함수 연결 |
| `src/components/UserSection.jsx` | 제목만 그리고 `UserInfo`에 다시 전달 |
| `src/components/UserInfo.jsx` | 이름·나이 표시, 폼 제출 시 변경 함수 호출 |

`Counter`는 props로 받은 함수를 버튼에 바로 연결합니다.

```jsx
<button onClick={decrementCount}>-</button>
<button onClick={resetCount}>Reset</button>
<button onClick={incrementCount}>+</button>
```

### 이 방식의 특징

상태를 소유한 곳이 `App` 한 곳이라 흐름을 따라가기 쉽습니다. 컴포넌트가 깊어질수록 중간 파일의 매개변수 목록이 길어집니다. 중간 컴포넌트는 값을 사용하지 않아도 시그니처에 그 값을 적어 두어야 합니다.

## 2. `usecontext`

### 문제

`props`에서는 `MainContent`, `CounterSection`, `UserSection`이 자기 화면과 관계없는 값을 전달만 합니다. 필요한 컴포넌트가 중간을 거치지 않고 같은 상태를 읽게 해야 합니다.

### 답

`src/context/AppContext.jsx`에서 통로와 공급자를 만듭니다.

1. `createContext()`로 빈 통로 `AppContext`를 만듭니다.
2. `AppProvider`가 `props`의 `App`과 같은 `useState`와 변경 함수를 가집니다.
3. 그 값들을 `value` 객체로 묶어 `AppContext.Provider`에 넣습니다.
4. `useAppContext()`가 `useContext(AppContext)`로 `value`를 꺼냅니다. Provider 밖에서 호출하면 에러를 던집니다.

```jsx
const value = {
  user, updateUserName, updateUserAge,
  count, decrementCount, incrementCount, resetCount,
};

return (
  <AppContext.Provider value={value}>
    {children}
  </AppContext.Provider>
);
```

`App.jsx`는 화면 전체를 `AppProvider`로 감쌉니다. `Header`와 `MainContent`에는 props를 넘기지 않습니다.

```jsx
<AppProvider>
  <div className="app">
    <Header />
    <MainContent />
  </div>
</AppProvider>
```

데이터를 쓰는 컴포넌트만 훅을 호출합니다.

| 파일 | 꺼내는 값 |
| --- | --- |
| `Header.jsx` | `user` |
| `Counter.jsx` | `count`, `incrementCount`, `decrementCount`, `resetCount` |
| `UserInfo.jsx` | `user`, `updateUserName`, `updateUserAge` |

`MainContent`, `CounterSection`, `UserSection`은 props가 없습니다. 자식 컴포넌트만 렌더합니다.

코드 안의 주석이 정리한 세 단어는 다음과 같습니다.

- Context: 전역 데이터 통로
- Provider: 데이터 공급
- useContext: 데이터 꺼내기

### 이 방식의 특징

중간 컴포넌트의 매개변수에서 전달용 props가 사라집니다. 상태 정의는 여전히 `useState`와 일반 함수이고, 위치만 `App`에서 `AppProvider`로 옮겨집니다. Provider로 감싼 트리 안의 컴포넌트만 `value`에 접근할 수 있습니다.

`Header.jsx`의 제목은 아직 `Props Drilling 방식`으로 남아 있습니다.

## 3. `redux`

### 문제

앱 전체가 공유하는 데이터를 한 창고에 두고, 컴포넌트는 그 창고를 직접 읽고 변경 요청을 보내야 합니다. 변경 규칙은 컴포넌트 밖, 상태 종류별 파일에 모아 둡니다.

### 답

창고는 `src/store/store.js`입니다. `configureStore`가 슬라이스 두 개를 하나의 상태로 합칩니다.

```jsx
export const store = configureStore({
  reducer: {
    counter: counterReducer,
    user: userReducer,
  },
});
```

`createSlice`는 상태, 액션, 리듀서를 한 번에 만듭니다.

| 파일 | `name` | 초기 상태 | 리듀서 |
| --- | --- | --- | --- |
| `counterSlice.js` | `"counter"` | `{ value: 0 }` | `increment`, `decrement`, `reset` |
| `userSlice.js` | `"user"` | `{ name: "홍길동", age: 25 }` | `updateName`, `updateAge` |

카운터 리듀서는 현재 상태만 받아 숫자를 바꿉니다.

```jsx
increment: (state) => { state.value += 1; },
decrement: (state) => { state.value -= 1; },
reset: (state) => { state.value = 0; },
```

사용자 리듀서는 두 번째 인자 `action`의 `payload`를 새 값으로 씁니다.

```jsx
updateName: (state, action) => { state.name = action.payload; },
updateAge: (state, action) => { state.age = action.payload; },
```

`dispatch(updateName("김미자"))`가 만들어지는 액션 형태는 주석에 적힌 대로입니다.

```jsx
{
  type: "user/updateName",
  payload: "김미자",
}
```

컴포넌트 연결은 아래와 같습니다.

| 파일 | 읽기 | 쓰기 |
| --- | --- | --- |
| `Header.jsx` | `useSelector(state => state.user)` | 없음 |
| `Counter.jsx` | `useSelector(state => state.counter.value)` | `dispatch(increment())`, `dispatch(decrement())`, `dispatch(reset())` |
| `UserInfo.jsx` | `useSelector(state => state.user)` | `dispatch(updateName(nameInput))`, `dispatch(updateAge(parseInt(ageInput)))` |
| `MainContent`, `CounterSection`, `UserSection` | 없음 | 없음 |

버튼 클릭부터 화면 갱신까지의 흐름은 `counterSlice.js` 주석과 같습니다.

```
버튼 클릭
 → dispatch(increment)
 → reducer 실행
 → state.value가 1 증가
 → 그 값을 구독하는 컴포넌트가 다시 렌더
```

`App.jsx` 주석이 정리한 사용 기준은 다음과 같습니다.

- Redux는 앱 전체가 공유하는 데이터 창고입니다.
- 어디서든 `useSelector`로 읽고 `dispatch`로 변경할 수 있습니다.
- Props를 여러 단계 넘기거나 컴포넌트가 많아질 때 사용합니다.
- 핵심은 `store` + `useSelector` + `dispatch`입니다.

### 현재 코드에서 연결이 빠져 있는 부분

`store`는 만들어져 있지만 `src/main.jsx`가 앱을 `Provider`로 감싸지 않습니다. `react-redux`의 `useSelector`와 `useDispatch`는 `Provider`가 넘겨 준 store가 있어야 동작합니다. 진입점은 지금 아래처럼 `App`만 렌더합니다.

```jsx
createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>,
);
```

store를 앱에 연결하려면 `main.jsx`에서 `Provider`로 감싸야 합니다.

```jsx
import { Provider } from "react-redux";
import { store } from "./store/store";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <Provider store={store}>
      <App />
    </Provider>
  </StrictMode>,
);
```

### 이 방식의 특징

상태 변경 규칙이 `counterSlice.js`, `userSlice.js`에 모여 있습니다. 컴포넌트는 액션을 보내기만 합니다. 카운터처럼 추가 데이터가 없는 액션은 `dispatch(increment())`이고, 이름·나이처럼 새 값이 필요한 액션은 `payload`를 인자로 넘깁니다.

## 세 방식을 나란히 보면

같은 동작이 코드에서 어디에 있는지만 다릅니다.

| 동작 | props | useContext | Redux |
| --- | --- | --- | --- |
| 상태 선언 | `App`의 `useState` | `AppProvider`의 `useState` | 각 slice의 `initialState` |
| 카운트 +1 | `setCount(count + 1)` | 같은 함수를 context `value`에 넣음 | `state.value += 1` |
| 이름 변경 | `setUser({ ...user, name })` | 같은 함수를 context `value`에 넣음 | `state.name = action.payload` |
| 화면이 값을 받음 | 함수 매개변수 | `useAppContext()` | `useSelector` |
| 화면이 값을 바꿈 | props로 받은 함수 호출 | context에서 꺼낸 함수 호출 | `dispatch(액션)` |
| 중간 컴포넌트 | props를 다시 전달 | 전달 없음 | 전달 없음 |

---

## 코드에 공통으로 있는 표기

세 폴더의 `UserSection.jsx`는 태그가 `<section>`이 아니라 `<setction>`입니다. `props`의 `CounterSection.jsx` 클래스 이름은 `setion`입니다. `usecontext`의 `Header` 제목은 `Props Drilling 방식`으로 남아 있습니다.

## 문제와 답

### 1. 세 폴더가 공유하는 상태 두 가지는 무엇인가?

**답.** 숫자 `count`(Redux에서는 `counter.value`)와 사용자 `user`(`name`, `age`)입니다. 초기 사용자는 홍길동, 25세이고 카운트 초기값은 0입니다.

### 2. 상태를 직접 읽고 바꾸는 컴포넌트는 어디인가?

**답.** `Header`는 사용자를 읽습니다. `Counter`는 숫자를 읽고 `+`, `−`, `Reset`으로 바꿉니다. `UserInfo`는 사용자를 읽고 폼 제출로 이름·나이를 바꿉니다. `MainContent`, `CounterSection`, `UserSection`은 공유 상태를 계산에 쓰지 않습니다.

### 3. `props`에서 `MainContent`가 하는 일은 무엇인가?

**답.** `App`에서 받은 `user`, `count`와 변경 함수를 용도별로 나눕니다. 카운터 관련 값은 `CounterSection`으로, 사용자 관련 값은 `UserSection`으로 다시 넘깁니다. 이 파일 자체는 그 값으로 화면을 그리지 않습니다.

### 4. `updateUserName`이 `{ ...user, name }`을 쓰는 이유는 무엇인가?

**답.** 기존 객체를 펼쳐서 `age`를 유지한 채 `name`만 교체하기 위해서입니다. `setUser(name)`처럼 문자열만 넣으면 `user.age`를 읽을 수 없게 됩니다. `updateUserAge`도 같은 방식으로 `age`만 바꿉니다.

### 5. Context의 세 역할은 코드에서 어디에 대응하는가?

**답.**

- 통로: `const AppContext = createContext()`
- 공급: `AppProvider`가 `value`를 `<AppContext.Provider>`에 넣음
- 꺼내기: `useAppContext()` 안의 `useContext(AppContext)`

`App`은 `<AppProvider>`로 화면을 감싸야 `Header`, `Counter`, `UserInfo`가 그 `value`를 읽을 수 있습니다.

### 6. `useAppContext()`를 Provider 밖에서 호출하면 어떻게 되는가?

**답.** 훅이 `context`가 없을 때 `throw new Error("useAppContext must be used within AppProvider")`를 실행합니다.

### 7. Redux에서 읽기와 쓰기는 어떤 함수인가?

**답.** 읽기는 `useSelector`입니다. store 상태의 일부를 고르고, 그 값이 바뀌면 컴포넌트가 다시 렌더됩니다. 쓰기는 `useDispatch`로 받은 `dispatch`입니다. `dispatch(increment())`처럼 액션을 보내면 해당 리듀서가 실행됩니다.

### 8. `increment`와 `updateName`의 인자 차이는 무엇인가?

**답.** `increment`는 추가 데이터 없이 상태를 1 올립니다. `dispatch(increment())`만 호출합니다. `updateName`은 사용자가 입력한 새 이름이 필요합니다. `dispatch(updateName(nameInput))`의 인자가 `action.payload`가 되고, 리듀서는 `state.name = action.payload`로 저장합니다. 나이는 `updateAge`가 같은 방식으로 `payload`를 `state.age`에 넣습니다.

### 9. `configureStore`의 `reducer` 키가 화면 코드와 어떻게 연결되는가?

**답.** `counter: counterReducer`로 등록했으므로 화면은 `state.counter.value`로 읽습니다. `user: userReducer`로 등록했으므로 화면은 `state.user`, `state.user.name`, `state.user.age`로 읽습니다.

### 10. 이름 폼과 나이 폼은 언제 공유 상태를 바꾸는가?

**답.** 제출(`onSubmit`) 때입니다. 입력 중 `onChange`는 `nameInput`, `ageInput`이라는 `UserInfo` 로컬 state만 바꿉니다. 이름은 `trim()` 결과가 있을 때, 나이는 값이 있고 `isNaN`이 거짓일 때 공유 상태를 갱신합니다. 성공하면 해당 입력칸을 빈 문자열로 되돌립니다.

### 11. Redux 폴더를 실행할 때 store가 연결되지 않는 이유는 무엇인가?

**답.** `store.js`는 `store`를 내보내지만 `main.jsx`가 `<Provider store={store}>`로 `App`을 감싸지 않습니다. `useSelector`와 `useDispatch`는 이 Provider가 있어야 store를 찾습니다.

### 12. 어떤 폴더를 고를지의 기준을 이 예제 주석대로 말하면?

**답.** 단계가 얕고 전달 값이 적으면 `props`로 충분합니다. 중간 컴포넌트가 값을 쓰지 않는데 전달만 반복되면 `useContext`로 필요한 곳에서 꺼냅니다. 주석 기준으로 props를 여러 단계 넘기고 컴포넌트가 많아지면 `store`에 모으고 `useSelector`와 `dispatch`로 다룹니다.
